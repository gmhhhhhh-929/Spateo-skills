# Spatial Balanced Sample

## Package paths

Run the relative commands below from this skill directory. Keep this subskill inside the complete `spateo-2d-alignment` directory.
The shared support tools are the fixed pre-zebrafish snapshot, located in
`../../pipelines/pairwise-rigid`. Verify entrypoints with its `skill.lock.yaml`.
This packaging restoration does not change alignment algorithms or defaults.


## Scope

Use this skill to create a lightweight working coordinate cache from a full
spatial transcriptomics coordinate table. The sample is for post-edit structure
review, component/triad QC, and candidate rigid preview after the suspicious
region has first been judged on full-data coordinates. Final outputs must still
be generated by replaying recipes on the full table.

This skill must not replace the full data or final h5ad.

## Locked Entrypoints

Use the locked GitHub/deployed release for the active project. For the
standard workflow release this is `v0.2.3`:

```text
../../pipelines/pairwise-rigid/scripts/sampling/create_balanced_spatial_sample.py
../../pipelines/pairwise-rigid/scripts/sampling/validate_sample_recipe_full_replay.py
```

Record entrypoint sha256 from `../../pipelines/pairwise-rigid/skill.lock.yaml`; fail on hash mismatch.

## Sampling Policy

Sample by `slice x component_rank` or `slice x component_id`, never by global
random sampling alone.

Default policy:

- target `300000` displayed review points with `--target-total-points 300000`;
- keep all components below `keep_all_below`;
- for larger components keep at least `min_per_component`;
- cap large components with `max_per_component` when a cap is configured;
- within each large component, use spatial grid-balanced selection so outlines
  and disconnected regions remain visible;
- read the clean coordinate schema by default, with final coordinates named
  `x/y/z`;
- preserve `cell_id`, slice, cell type, component id/rank, and final
  coordinate columns. The `cell_id` column must already be the clean
  h5ad-derived id; do not sample from a table whose user-facing id is an
  internal row number such as `slice_id:0`.
- write component fields that the viewer can consume, usually
  `sample_component_id` and `sample_component_rank`, while preserving any
  original `component_id` and `component_rank` columns if they were already in
  the input.

Small components and tissue islands are high priority; do not let them vanish
from the review cache.

## Workflow

1. Start from a replayed slice-level baseline clean coordinate CSV.
2. Detect components on that same baseline, or reuse component labels if the
   same coordinate state is proven by hash.
3. Run `create_balanced_spatial_sample.py`.
4. Build a sampled pointcloud viewer from the sampled CSV with component mode
   enabled. The viewer should show component labels such as `SL59 rank2 id7`.
5. Use sampled data for post-edit visual QC and candidate rigid recipes. Do
   not use it as the only surface for the initial manual decision.
6. Before trusting the sampled workflow, run
   `validate_sample_recipe_full_replay.py` with a smoke-test recipe to prove a
   sampled recipe replays identically on the full table subset.
7. Final accepted recipes must be replayed once on full data.

## Required Outputs

The viewer summary must report the resolved component columns. For a standard
balanced sample this is usually:

```text

```

For sampled-to-full validation:

```text
qc/sample_full_replay_consistency.json
```

## Guardrails

- Do not tune final coordinates directly on full CSV during iteration.
- Do not replace full-data manual review with balanced300k. Use full-points
  review first, then balanced300k for speed after edits.
- Do not let balanced samples normalize, renumber, or invent cell ids. They
  must carry through the clean ids from the full coordinate table.
- Do not drop component labels from the sampled CSV; without them the review
  viewer cannot tell the user which colored region is `rank2` or a small
  anchor island.
- Do not generate a new full corrected CSV for every candidate.
- Keep candidate outputs as recipes/deltas plus small review HTML.
- Compose full data only for baseline replay, smoke-test validation, and final
  accepted output.
